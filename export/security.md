# Security Best Practices

Security is the one area where "good enough" isn't. A performance bug costs you latency. A security bug costs you customer data, regulatory fines, and the kind of headlines that end careers. The uncomfortable truth is that most security incidents aren't sophisticated attacks — they're basic mistakes: hardcoded credentials, missing input validation, overly permissive access, unpatched dependencies. The fix isn't hiring a security team and hoping they catch everything. It's building security into the way every engineer writes code, reviews code, and deploys code.

**The goal: make the secure path the easy path, so developers do the right thing by default.**

---

## Principles

These principles apply regardless of technology, framework, or architecture.

### 1. Defense in Depth

Never rely on a single security control. Layer defenses so that when (not if) one fails, others catch the breach.

```
Internet → WAF → Load Balancer → API Gateway (auth) → Application (authz) → Database (row-level security)
```

If the WAF misses a malicious request, the API gateway blocks it for lacking authentication. If auth is bypassed, authorization checks prevent access to other users' data. If authorization is bypassed, the database only returns rows the authenticated identity owns.

No single layer is perfect. The combination is what provides security.

### 2. Least Privilege

Every component — user, service, process, API key — should have the minimum permissions required to do its job, and no more.

| Scope | What Least Privilege Looks Like |
|-------|--------------------------------|
| Database credentials | Read-only for services that only read. Per-schema access, not full-database access. |
| API keys | Scoped to specific endpoints or operations. Short-lived. Rotatable. |
| Service accounts | Can only call the specific downstream services it needs. |
| File system | Application runs as non-root. Write access only to specific directories. |
| Cloud IAM | Narrowest possible role. No wildcards in resource ARNs. |
| Developer access | Production access via break-glass, not standing permissions. |

**Test this:** If you remove a permission and nothing breaks, it shouldn't have been there.

### 3. Fail Secure

When something goes wrong, the system should deny access, not grant it.

```
// Fail open (WRONG) — if auth service is down, let the request through
if (authService.isAvailable()) {
    authService.checkPermission(user, resource);
}
// User gets access when auth service is down

// Fail secure (RIGHT) — if auth service is down, deny the request
try {
    authService.checkPermission(user, resource);
} catch (ServiceUnavailableException e) {
    throw new AccessDeniedException("Unable to verify permissions");
}
```

This applies everywhere: default-deny firewall rules, default-deny authorization policies, error pages that don't leak information.

### 4. Don't Trust Input — Ever

Every piece of data that crosses a trust boundary — user input, API parameters, HTTP headers, file uploads, webhook payloads, data from other services — is potentially malicious until validated.

Trust boundaries:
- Browser → Server
- External API → Your service
- Message queue → Consumer
- File system → Application
- Database → Application (yes, even data you wrote)

## Authentication

Authentication is "who are you?" Get it wrong and attackers impersonate your users.

### Password Handling

**Never store plaintext passwords.** This is non-negotiable.

| Practice | Do | Don't |
|----------|-----|-------|
| Storage | Hash with bcrypt, scrypt, or argon2 | MD5, SHA-1, SHA-256 without salt, or plaintext |
| Salt | Unique per-password, generated by the hashing library | Shared/global salt, no salt |
| Comparison | Constant-time comparison | Early-return string comparison (timing attack) |
| Transmission | Over TLS only | Plaintext HTTP |
| Reset | Time-limited token sent to verified email | Security questions, emailing the password |

### Token-Based Authentication

| Concern | Best Practice |
|---------|--------------|
| Token storage (browser) | HttpOnly, Secure, SameSite cookies. Never localStorage. |
| Token lifetime | Short-lived access tokens (15-60 min). Longer-lived refresh tokens (hours-days). |
| Token revocation | Maintain a revocation list or use short-lived tokens that don't need explicit revocation. |
| Token content | Don't store sensitive data in JWTs — they're base64-encoded, not encrypted. Anyone can read them. |
| Signing | Use asymmetric keys (RS256/ES256) for cross-service verification. Symmetric (HS256) only for single-service use. |

### Multi-Factor Authentication

MFA should be available for all user-facing applications and required for:
- Admin/privileged accounts
- Access to production systems
- Financial transactions above a threshold
- Account recovery flows

### Session Management

| Rule | Why |
|------|-----|
| Regenerate session ID after login | Prevents session fixation attacks |
| Set absolute session timeout | Limits exposure window if session is stolen |
| Set idle timeout | Auto-logout after inactivity |
| Invalidate session on logout | Server-side invalidation, not just deleting the cookie |
| Bind session to user metadata | IP change + user agent change = re-authenticate |

## Authorization

Authorization is "what are you allowed to do?" Authentication without authorization is a locked front door with no locks on any rooms inside.

### Principles

1. **Enforce on the server.** Client-side authorization (hiding buttons, disabling menu items) is UX — not security. The server must verify every request.

2. **Check at the resource level.** Don't just check "can this user access the orders API" — check "can this user access *this specific order*."

    ```
    // Insufficient — checks role but not ownership
    if (user.hasRole("customer")) {
        return orderService.getOrder(orderId);
    }

    // Correct — checks that this user owns this order
    Order order = orderService.getOrder(orderId);
    if (!order.belongsTo(user.getId())) {
        throw new ForbiddenException();
    }
    ```

3. **Default deny.** If no rule explicitly grants access, the answer is no.

4. **Separate data access from business logic.** Authorization decisions should be made in a consistent layer (middleware, interceptor, policy engine) — not scattered throughout business logic.

### Common Authorization Models

| Model | How It Works | Best For |
|-------|-------------|----------|
| **RBAC** (Role-Based) | Users have roles (admin, editor, viewer). Roles have permissions. | Most applications. Simple, well-understood. |
| **ABAC** (Attribute-Based) | Decisions based on user attributes, resource attributes, and context (time, location). | Complex policies. "Editors can edit documents in their department during business hours." |
| **ReBAC** (Relationship-Based) | Decisions based on relationships between entities. "User X is a member of org Y, which owns resource Z." | Multi-tenant systems, social networks, document sharing (Google Docs model). |

### Insecure Direct Object References (IDOR)

One of the most common authorization vulnerabilities. The user manipulates an ID in the request to access another user's data.

```
GET /api/orders/12345   ← the user's order
GET /api/orders/12346   ← someone else's order — does the server check?
```

**Prevention:** Every data access must verify that the authenticated user is authorized to access that specific resource. Use the authenticated user's identity from the session — never trust a user ID sent in the request body or URL.

## Input Validation

For API-level request validation (required fields, formats, ranges, returning all errors at once), see API Design — Request Validation. This section focuses on security-specific validation concerns.

### Validate Everything at the Boundary

| Input Source | What to Validate |
|-------------|-----------------|
| Query parameters | Type, length, range, allowed values |
| Request body | Schema validation, required fields, type checking |
| Path parameters | Format (UUID, numeric ID), existence |
| HTTP headers | Expected format, reasonable length |
| File uploads | File type (magic bytes, not just extension), size, content scanning |
| Webhook payloads | Signature verification, schema validation |

### Validation Rules

1. **Allowlist over denylist.** Define what's allowed, not what's forbidden. You'll never enumerate every possible attack string.

    ```
    // Denylist (WRONG) — you'll miss something
    if (input.contains("<script>")) reject();

    // Allowlist (RIGHT) — only accept what you expect
    if (!input.matches("[a-zA-Z0-9 ]{1,100}")) reject();
    ```

2. **Validate on the server.** Client-side validation is UX. Server-side validation is security. You need both, but only the server matters for security.

3. **Validate before use.** Validate input as early as possible — at the API boundary, before it enters business logic or storage.

4. **Use typed parsing, not string manipulation.** Parse "123" into an integer and validate the integer, rather than checking the string with regex.

### Injection Prevention

| Attack | Vector | Prevention |
|--------|--------|-----------|
| **SQL injection** | Unsanitized input in SQL queries | Parameterized queries / prepared statements. Never concatenate user input into SQL. |
| **NoSQL injection** | Unsanitized input in query objects | Use driver-provided query builders. Validate input types strictly. |
| **Command injection** | User input passed to shell commands | Avoid shelling out. If unavoidable, use parameterized execution — never string concatenation. |
| **XSS** | User input rendered in HTML without encoding | Output encoding appropriate to context (HTML, JS, URL, CSS). Use framework auto-escaping. |
| **Path traversal** | User input in file paths (`../../etc/passwd`) | Normalize paths and verify they stay within the intended directory. Never concatenate user input into file paths. |
| **Header injection** | User input in HTTP headers (CRLF injection) | Strip newline characters from any user input used in headers. |
| **Template injection** | User input in template strings | Never pass user input as template source. Use sandboxed template engines. |

The single most important rule: **never concatenate user input into queries, commands, or templates.** Use parameterized/prepared interfaces.

## Secrets Management

### The Rules

1. **Never commit secrets to version control.** Not in code, not in config files, not in comments, not in "temporary" test files. Treat any secret that was ever in a repo as compromised.

2. **Never log secrets.** Redact secrets from log output. Watch for libraries that log full request/response bodies — they'll log your API keys.

3. **Use a secrets manager.** Store secrets in a dedicated system (Vault, cloud secrets manager, etc.) and fetch them at runtime. Not in environment variables if you can avoid it (they leak in crash dumps, process listings, and child processes).

4. **Rotate regularly.** Every secret should have a rotation policy. Automate rotation so it's painless.

5. **Scope narrowly.** A secret that grants access to everything is a single point of compromise. Use per-service, per-environment secrets with minimal permissions.

### Environment-Specific Secrets

| Requirement | Practice |
|------------|----------|
| Dev/test environments | Use dummy/fake secrets. Never use production secrets in lower environments. |
| CI/CD pipelines | Inject secrets from the CI system's secret store. Never echo them to logs. |
| Production | Fetch from secrets manager at startup. Never bake into container images. |
| Local development | Use `.env` files (gitignored) or a local secrets manager. Never share secrets via Slack/email. |

### What to Do When a Secret Leaks

1. **Rotate immediately.** Don't investigate first. Rotate now, investigate later.
2. **Audit access logs.** Determine if the leaked secret was used by anyone unauthorized.
3. **Determine scope.** What can this secret access? What's the blast radius?
4. **Notify.** If customer data may have been accessed, follow your incident response and disclosure procedures.
5. **Prevent recurrence.** Add pre-commit hooks that scan for secrets. Run periodic repo scans.

## Dependency Security

Your application is only as secure as its weakest dependency. And you probably have hundreds of them.

### Practices

| Practice | Why |
|----------|-----|
| **Scan dependencies for known vulnerabilities** | CVE databases are public. Attackers scan for apps using vulnerable versions. |
| **Run scans in CI/CD** | Catch new vulnerabilities before they reach production. |
| **Update regularly** | Don't let dependencies get years behind. Small, frequent updates are safer than large, infrequent ones. |
| **Pin versions** | Use exact versions or lock files, not ranges. Know exactly what you're running. |
| **Evaluate before adopting** | Check maintenance status, known vulnerabilities, download trends, and license. |
| **Minimize dependencies** | Every dependency is attack surface. If you can write 20 lines instead of importing a library, consider it. |

### Supply Chain Attacks

Attackers increasingly target the dependency itself — publishing malicious packages, typosquatting popular names, or compromising maintainer accounts.

**Mitigations:**
- Use a private registry or proxy that caches approved packages
- Verify package checksums/signatures
- Monitor for unexpected dependency changes in pull requests
- Be wary of packages with low download counts or recent ownership changes

## API Security

| Concern | Best Practice |
|---------|--------------|
| **Authentication** | Require authentication on every endpoint. No "public" APIs that accidentally expose data. |
| **Rate limiting** | Prevent abuse and brute-force attacks. Apply per-user and per-IP. |
| **Request size limits** | Cap request body size. A 10GB POST can exhaust memory. |
| **HTTPS everywhere** | No exceptions. Redirect HTTP to HTTPS. Use HSTS. |
| **CORS** | Restrict allowed origins. Never use `Access-Control-Allow-Origin: *` on authenticated endpoints. |
| **Error responses** | Return generic error messages. Never expose stack traces, database errors, or internal paths to clients. |
| **Deprecation** | When retiring an endpoint, disable it — don't just stop documenting it. |

## Logging and Auditing for Security

### What to Log

| Event | Why |
|-------|-----|
| Authentication attempts (success and failure) | Detect brute-force attacks, credential stuffing |
| Authorization failures | Detect privilege escalation attempts |
| Input validation failures | Detect scanning/probing |
| Administrative actions | Audit trail for compliance |
| Data access patterns | Detect unusual data exfiltration |
| Configuration changes | Detect unauthorized modifications |

### What NOT to Log

Never log passwords, credentials, tokens, PII, or other sensitive data. See Logging for the complete never-log list and log security practices.

### Log Integrity

- Send logs to a tamper-evident store (append-only, separate from the application)
- Attackers who compromise a system often try to delete logs to cover their tracks
- Set retention policies that meet compliance requirements

## Common Vulnerability Patterns

### Mass Assignment

Accepting all fields from a request and mapping them directly to your data model. An attacker adds fields you didn't intend to be settable.

```
// User sends: { "name": "Alice", "role": "admin" }
// If you blindly map all fields, the user just made themselves an admin
user.updateFromRequest(requestBody);  // sets name AND role
```

**Fix:** Explicitly define which fields are accepted from user input. Use allowlists or dedicated DTOs.

### Broken Function-Level Authorization

An endpoint exists for admins, but there's no authorization check — any authenticated user can call it.

```
// The UI only shows this button to admins
// But the API doesn't check — any user who knows the URL can call it
POST /api/admin/users/delete
```

**Fix:** Authorization checks on every endpoint, not just the ones you think regular users will find.

### Race Conditions in Security Checks

```
1. Thread A: Check user has $100 balance → yes
2. Thread B: Check user has $100 balance → yes
3. Thread A: Deduct $100 → balance = $0
4. Thread B: Deduct $100 → balance = -$100  (double spend)
```

**Fix:** Use database-level transactions, optimistic locking, or atomic operations for security-sensitive state changes.

### Verbose Error Messages

```
// Leaks information
{ "error": "User admin@company.com not found in table users (PostgreSQL 14.2)" }

// Safe
{ "error": "Invalid credentials" }
```

Never tell an attacker whether the username or password was wrong, what database you use, what the internal path structure looks like, or what version of anything you're running.

## Security in the SDLC

Security isn't a phase — it's a practice that runs through the entire development lifecycle.

| Phase | Security Activity |
|-------|------------------|
| **Design** | Threat modeling. Identify trust boundaries, data flows, and attack surface. |
| **Code** | Use safe-by-default libraries. Follow input validation rules. Run SAST (static analysis). |
| **Code review** | Check for auth/authz, input validation, secrets exposure, error handling. |
| **Test** | Include security test cases. Test for IDOR, injection, auth bypass. |
| **Build** | Dependency scanning (SCA). Container image scanning. |
| **Deploy** | Secrets injected at runtime. Minimal container images. Non-root processes. |
| **Operate** | Monitor security logs. Rotate secrets. Patch dependencies. Run periodic penetration tests. |

### Threat Modeling (Simplified)

For every feature or system, ask:
1. **What are we building?** (data flow diagram)
2. **What can go wrong?** (STRIDE: Spoofing, Tampering, Repudiation, Information Disclosure, Denial of Service, Elevation of Privilege)
3. **What are we going to do about it?** (mitigations for each threat)
4. **Did we do a good enough job?** (review and test)

You don't need a formal threat model for every PR. But for any new system, new data flow, or new external integration, spend 30 minutes on this. It will save you weeks of remediation later.

## Quick Reference Checklist

- [ ] **Authentication** enforced on every endpoint that accesses user data
- [ ] **Authorization** checks at the resource level — not just role checks, but ownership checks
- [ ] **Input validated** at the server boundary — allowlist, typed parsing, length limits
- [ ] **Parameterized queries** for all database access — no string concatenation
- [ ] **Secrets** never in source control, logs, or error messages
- [ ] **Dependencies scanned** for known vulnerabilities in CI/CD
- [ ] **HTTPS everywhere** — no plaintext HTTP, HSTS enabled
- [ ] **Error messages** are generic — no stack traces, internal paths, or database details in responses
- [ ] **Passwords hashed** with bcrypt/scrypt/argon2 — never MD5, SHA, or plaintext
- [ ] **Tokens** stored in HttpOnly Secure cookies — never localStorage
- [ ] **CORS** restricted to known origins — no wildcards on authenticated endpoints
- [ ] **Rate limiting** on authentication endpoints and any resource-intensive operations
- [ ] **Audit logging** for auth attempts, authorization failures, and admin actions
- [ ] **Least privilege** applied to all service accounts, API keys, and database credentials
- [ ] **Fail secure** — deny access on error, not allow
